Now **Part 1: The Building Blocks**.
**Repository (Repo):** the project container with files and full history.
**Organization (Org):** a shared GitHub account where teams and projects live.
**Fork:** your copy of someone else’s repo in your account.
**Clone:** copy a repo to your local machine.
**Push** sends local commits up to a remote; **pull** brings remote changes down.

[JAMIE]
So local versus remote is the core mental model.

[ALEX]
Right. **Remote** is any hosted repo connection. **Origin** is usually your default remote after clone. **Upstream** is the original project you forked from. **Downstream** is your fork or derivative receiving upstream changes.
And yes, keep the words straight: **local** is your computer, **remote** is hosted.

[JAMIE]
Can we include the two practical remote moments?

[ALEX]
Yes:
**To see your remotes:** `git remote -v`
**To add a remote:** `git remote add upstream <url>`

Next, **.gitignore**. It tells Git what not to track.
**Why use .gitignore?** avoid noise, avoid secrets, avoid generated files.
**Example `.gitignore`:** `.env`, `node_modules/`, `dist/`, `.DS_Store`, `Thumbs.db`.
If a file is already tracked, remove it from tracking before ignore rules apply.

[JAMIE]
Then branches and commits?

[ALEX]
Yes. **Branch** is an independent line of work.
**Common branch names:** `main`, `develop`, `feature/...`, `fix/...`, `docs/...`.
**Commit** is a saved snapshot plus message.
**Diff** is the before/after view of changes.

[ALEX]
Now **Part 2: Collaboration Workflow**.
**Issue:** track bugs, ideas, and tasks.
**Pull Request (PR):** propose merging changes from one branch to another.
PRs can be **draft** when work is not ready for final review.
**Code Review:** feedback loop before merge.
**Merge:** combine approved changes.
**Merge Conflict:** same area changed in incompatible ways; needs manual resolution.

[JAMIE]
And governance terms?

[ALEX]
**Label** categorizes issues and PRs.
**Milestone** groups work toward a target.
**Project (GitHub Projects)** tracks work across issues and PRs in boards/views.
**Status check** is automated validation on a PR, often required before merge.

**Maintainer:** sets direction and final decisions.
**Contributor:** submits code, docs, tests, ideas.
**Triage:** classifies and routes incoming issues.

Now **Part 5: Technical GitHub Concepts**.
**HEAD:** your current checkout pointer.
**Detached HEAD:** HEAD points to a commit, not a branch.
**Why it happens:** checkout of raw commit/tag.
**What this means:** commits can become hard to find from branch history.
**How to fix it:** create/switch to a branch and continue there.

[JAMIE]
Include stash and rebase with practical boundaries.

[ALEX]
Absolutely.
**Stash:** temporarily save uncommitted changes.
**Common workflow:** stash, switch, pull/fix, return, apply stash.
**Stash commands:** `git stash`, `git stash list`, `git stash pop`, `git stash apply`.

**Rebase** rewrites commit base for a cleaner linear history.
**Merge** preserves branch history; **rebase** rewrites it.
**When to use rebase:** clean local commits before PR.
**When NOT to rebase:** shared public branch others depend on.
**Basic rebase workflow:** fetch, rebase onto target, resolve conflicts, continue.

[JAMIE]
And the safety section: cherry-pick, fetch vs pull, force push, hash IDs.

[ALEX]
Yes.
**Cherry-pick:** apply one specific commit to another branch.
**When to use:** targeted fixes without merging whole branch.

**Fetch vs Pull:**
Use **fetch** to inspect updates safely first.
Use **pull** when you’re ready to integrate immediately.

**Force Push:** history rewrite on remote.
**When force push is okay:** your own feature branch with team awareness.
**When force push is NEVER okay:** protected/shared branches like `main`.
**Safer alternative:** `--force-with-lease`.
**Why force push is needed after rebase:** commit IDs changed, so remote history must be updated intentionally.

**SHA / Hash:** unique commit fingerprint, often shortened in UI.
