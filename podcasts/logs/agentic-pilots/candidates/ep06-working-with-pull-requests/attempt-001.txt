[ALEX]

Make it descriptive enough that someone scanning PR titles understands what you changed. The Description field is where you explain the why and the what. Use the PR template if one exists. Break it into sections: Summary (what changed), Changes (which files and why), Related Issues (link to the issue with "Closes #XX"), and Testing (how you verified this works).

[PAUSE]

[JAMIE]
Let's talk about the description structure in more detail.

[ALEX]
A strong PR description answers four questions: What changed? Why did it change? How was it tested? What should I pay attention to? These four guide a reviewer through the thought process without having to read the entire diff.

[ALEX]
Using GitHub's automatic issue linking: include "Closes #XX" where XX is the issue number. When the PR merges, GitHub automatically closes that issue. You don't need to close issues manually—just use the right keyword.

[ALEX]
A Before/After structure is highly effective. Show what the code looked like before your change and what it looks like after. The reviewer gets a mental snapshot instantly—no need to parse the diff line by line.

[ALEX]
Here's a template: Summary (one or two sentences of what changed), Changes (a bulleted list of files and modifications), Related Issues (Closes #XX), Testing (what you tested and how). Not every section applies to every PR, but filling in a few sentences per section makes a real difference for the reviewer.

[PAUSE]

[JAMIE]
Let's cover Common Description Mistakes. What's the anti-pattern?

[ALEX]
Experienced contributors stumble on these: no context or linked issue, no explanation of which file changed or why it matters. When a reviewer sees this, they have to open the diff, figure out what file changed, read every line, and guess at the intent.

[ALEX]

[ALEX]
The payoff: the good description tells the reviewer everything. The bad one forces investigation.
