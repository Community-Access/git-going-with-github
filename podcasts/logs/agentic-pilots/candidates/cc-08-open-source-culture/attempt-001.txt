What does the learner do first?

[ALEX]
Start with a guided reflection. Read the project’s CODE_OF_CONDUCT and CONTRIBUTING guidance, then post a short comment about what helps a community feel welcoming and inclusive.

[JAMIE]
Give me an example reflection comment.

[ALEX]
Something like: “I will begin reviews by naming what works, then raise one specific concern with a suggested next step. I will also ask for clarification with concrete context when I’m blocked.”

[JAMIE]
And triage?

[ALEX]
Pick an open issue and recommend or apply a fitting label. Common choices: bug, enhancement, documentation, and good first issue. Read title, description, and timeline before acting.

[JAMIE]
Example triage recommendation?

[ALEX]
Issue: “Welcome page is slow on mobile.” Recommendation: bug. Why: unexpected behavior that affects user experience.

[PAUSE]

[JAMIE]
What are alternate approaches if learners want options?

[ALEX]
Three good paths: reflect on CODE_OF_CONDUCT implications, reflect on CONTRIBUTING workflow expectations, or compare this project’s norms with another open source project.

[JAMIE]
What matters most?

[ALEX]
A thoughtful, specific reflection plus a justified triage decision. The point is understanding that open source has social norms and decision habits, not just technical tasks.

[JAMIE]
Where are the authoritative sources?

[ALEX]
Use GitHub Docs, GitHub Changelog, and official project governance docs. Keep a section-level source map so each major section is backed by a named source.

[ALEX]

[JAMIE]
Before communication details, what workflow context should they know?

[ALEX]
GitHub Flow. It is the standard contribution workflow used in this workshop.

[JAMIE]
Walk the six steps.

[ALEX]
Create branch, make focused changes, commit clearly, open PR early, discuss and revise in review, merge when approved. One branch, one scoped change.

[JAMIE]
Why this model works?

[ALEX]
Main stays deployable, PRs centralize discussion, and small changes are easier to review safely.

[JAMIE]
How does that compare with Git Flow?

[ALEX]
Git Flow uses multiple long-lived branches and release cycles. GitHub Flow is lighter and faster for continuous collaboration. You may still see Git Flow in release-heavy or legacy setups, but this workshop uses GitHub Flow for clarity and accessibility.

[JAMIE]
Unwritten rule?

[ALEX]
One thing per branch. It keeps review focused and history understandable.

[JAMIE]
Learning cards takeaway for GitHub Flow?

[ALEX]
Keep changes small, open PRs with clear intent, and keep conversation tied to concrete code and evidence.

[PAUSE]

[JAMIE]
Now fork hygiene.

[ALEX]
Keep your fork up to date so your PRs are clean and conflicts stay manageable.

[JAMIE]
Methods?

[ALEX]
Method 1: GitHub web sync button.
Method 2: command line—one-time upstream remote setup, then fetch upstream and merge or rebase into your branch.
Method 3: GitHub Desktop sync flow.

[JAMIE]
When should they sync?

[ALEX]
Before starting new work, before opening a PR, and after upstream has significant changes.

[JAMIE]
Learning cards summary?

[ALEX]
Sync early, sync often, and verify you are on the intended branch before you start.

[PAUSE]

[JAMIE]
Commit messages next.

[ALEX]
Use a clear format: first line is required summary, optional body explains why and context, optional footer links issues or metadata.

[JAMIE]
Atomic commits?

[ALEX]
Each commit should represent one coherent change.

[JAMIE]
Common mistakes?

[ALEX]
Vague summaries, mixed unrelated edits, and messages that describe mechanics but not intent.

[JAMIE]
Good commit messages in practice?

[ALEX]
“docs: clarify issue triage label guidance for newcomers” is better than “update stuff.”

[JAMIE]
Learning cards takeaway?

[ALEX]
If someone scans history later, they should quickly understand what changed and why.

[PAUSE]

[JAMIE]
Now the communication layer itself.

[ALEX]
Open source communication is mostly written, asynchronous, and public. That means clarity, tone, and context carry extra weight.

[JAMIE]
Anatomy of helpful feedback?

[ALEX]
1) acknowledge what works, 2) identify specific concern, 3) explain impact, 4) suggest a path forward when possible, 5) signal concern severity.

[JAMIE]
Language and tone rules?

[ALEX]
Prefer “we” or code-focused phrasing over person-focused blame. Use tentative language when uncertain. Respect cultural and language diversity. Avoid false urgency.

[JAMIE]
Commenting etiquette?

[ALEX]
Be specific, be kind, separate facts from assumptions, and keep suggestions actionable.

[PAUSE]

[JAMIE]
Final checkpoint?

[ALEX]
You can point to your reflection comment, explain your triage and label choice, and describe how you would continue in a real project thread.

[JAMIE]
And if someone freezes in the moment?

[ALEX]
Read the latest factual signal, check issue/branch/PR status, then ask for help with concrete context. That is effective, respectful open source collaboration.
