[ALEX]
Episode 5 is all about working with GitHub issues. Today we are turning filing, searching, filtering, commenting, and managing issues into a practical habit, not just a set of menu clicks.

[JAMIE]
I will keep us honest when the page gets busy, because issues look simple until you have to find the right one, read the thread, and decide what to do next.

[PAUSE]

[ALEX]
Here is the big idea: an issue is a unit of work, a bug report, or a feature request. It is where a repository collects problems, questions, and plans in one place.

[JAMIE]
So this chapter is really about participation. You are not just reading a list, you are learning how to join the conversation and leave a useful trace.

[ALEX]
Exactly. And the chapter has a nice rhythm: file a new issue, read existing issues, filter and search, comment, react, assign, label, and connect issues to pull requests when work is ready.

[PAUSE]

[JAMIE]
Set the scene for the workshop version.

[ALEX]
The workshop recommendation for Chapter 5 is to treat Challenges 2 and 3 as the core practice. Challenge 2 is creating your first issue. Challenge 3 is commenting and @mentioning. If your repository supports it, the optional extension is adding a sub-issue.

[JAMIE]
What should the learner keep in mind before they start?

[ALEX]
The key habit is to use the issue page as a workspace. Read the title, the body, the labels, the assignees, the milestone, and the timeline before acting. That gives you the context you need to make a good next move.

[ALEX]
The challenge set is simple in structure. File one clear issue. Leave one helpful comment with an @mention. Then, if enabled, split a larger task into a sub-issue. Each task should leave evidence in the issue thread or metadata.

[PAUSE]

[JAMIE]
What is the first step someone should take?

[ALEX]
Start with the first challenge: create a new issue in the Learning Room repository. Keep the title specific and the body descriptive. A good issue tells the reader what is wrong, what is missing, or what needs to happen next.

[JAMIE]
Can you give examples?

[ALEX]
Sure. A strong title might be, "Keyboard shortcut table needs NVDA modifier correction." Another could be, "Broken link in setup guide." In the body, explain the problem, add context, and say what you expected instead.

[ALEX]
If you need a pattern, use a structure like this: what happened, what you expected, how to reproduce, environment, and any extra context. Markdown helps here, so use lists, code blocks, task lists, and links when they make the issue easier to read.

[PAUSE]

[JAMIE]
What are the issue basics people need to know?

[ALEX]
An issue usually has a title, a body written in Markdown, labels, assignees, and maybe a milestone. The title should be short and clear. The body should provide enough detail that someone else can act without guessing.

[JAMIE]
And the labels and assignees?

[ALEX]
Labels help sort and prioritize. Assignees show who is responsible. Milestones group issues around a release or project goal. Those fields turn an open-ended note into trackable work.

[PAUSE]

[JAMIE]
How does someone find the Issues area?

[ALEX]
From a repository page, you can go to the Issues tab in the top navigation. If you know the direct URL, you can open the repository’s issues list directly too. On the page, you will see a list of issues with filters and search tools near the top.

[ALEX]
The list view usually shows the issue title, number, author, labels, and whether it is open or closed. That summary is important because you can scan a lot of work quickly before deciding what to open.

[JAMIE]
What should they listen for on that list?

[ALEX]
Listen for the status, the labels, and the author. Those details tell you whether the issue matches what you are looking for and whether it is already handled.

[PAUSE]

[JAMIE]
Let’s talk about filtering and searching.

[ALEX]
The Issues list supports both filter buttons and a search bar with qualifiers. You can narrow by label, author, assignee, milestone, and whether the issue is open or closed. You can also search with terms like is:open label:bug.

[JAMIE]
So the filters are not just convenience.

[ALEX]
Right. They are how you reduce noise. Open issues show active work. Closed issues show completed or resolved work. If you need bugs only, filter by label. If you need your own tasks, filter by assignee. If you want a milestone view, use that qualifier too.

[ALEX]
A useful search might look like this: is:open label:bug assignee:@me. Another might be is:closed author:octocat milestone:"v1". The exact syntax can vary by repository setup, but the idea is the same: ask for the slice you need.

[PAUSE]

[JAMIE]
What happens when someone opens a single issue?

[ALEX]
They land on the issue page, which is where the story lives. The title sits at the top, the body explains the problem, and the timeline shows comments, edits, references, reactions, and other activity.

[JAMIE]
So the timeline is not just commentary.

[ALEX]
No, it is the record of what happened. It can include comments, label changes, assignments, cross-references, closing events, and reopen events. When you read an issue well, you are reading the history of the work.

[PAUSE]

[JAMIE]
How should someone leave a comment?

[ALEX]
Scroll to the comment box, type a useful response, and submit it. If you are adding context, asking a question, or sharing a check-in, keep the comment direct and relevant. You can also use Markdown in comments just like in issue bodies.

[JAMIE]
What about reactions?

[ALEX]
Reactions are lightweight feedback. A thumbs up, a heart, or a thinking face can say, "I saw this," "I agree," or "I need more time." They are not a replacement for a real comment, but they are a useful signal.

[ALEX]
If you need to mention someone, use @ followed by their username. That notifies them and brings them into the thread. It is one of the simplest ways to connect people to the right issue.

[PAUSE]

[JAMIE]
What is the best way to file a new issue?

[ALEX]
Choose New issue from the Issues list, pick a template if one exists, or open a blank issue if that fits. Then write a title that says what the issue is, not just how you feel about it. After that, use the body to explain the situation in enough detail that someone else can act on it.

[JAMIE]
Can the body include structured Markdown?

[ALEX]
Absolutely. Use code blocks for errors or snippets, lists for steps, task lists for follow-up work, and links for references. Good formatting makes the issue easier to scan and easier to act on.

[ALEX]
If the repository uses a form with fields like what happened, what you expected, how to reproduce, environment, and additional context, fill those out carefully. Those prompts exist to help you write a stronger report.

[PAUSE]

[JAMIE]
What about assigning and labeling while you file?

[ALEX]
You can often set labels from the sidebar and assign the issue there too. If you are filing something for yourself, assign it to yourself. If someone else owns it, assign them instead. Labels should match the problem, like bug, enhancement, or documentation.

[JAMIE]
How do issues relate to pull requests?

[ALEX]
They are closely connected. An issue can describe the problem, and a pull request can reference that issue with a closing keyword or a #number reference. That keeps the conversation tied together and makes the final history easy to follow.

[PAUSE]

[JAMIE]
Show me the cross-referencing part.

[ALEX]
If you mention another issue in a comment with #number, GitHub turns it into a reference. If a pull request description says "Closes #42," merging the pull request can close the issue automatically. You can also reference issues across repositories when needed.

[JAMIE]
And closing or reopening?

[ALEX]
Closing means the issue is no longer active. It might be fixed, answered, or no longer needed. If the problem returns or the decision changes, you can reopen the issue and continue the thread.

[PAUSE]

[JAMIE]
Let’s cover the terminal alternative too.

[ALEX]
From your clone, you can use gh issue commands instead of the web UI. For example, gh issue list shows issues, gh issue view 42 opens one issue, gh issue comment 42 --body "I can work on this" leaves a comment, and gh issue create starts a new issue from the terminal.

[JAMIE]
That is helpful for anyone who prefers the command line.

[ALEX]
Yes, and it matches the same mental model. The interface changes, but the work stays the same: read the issue, decide on the next action, and leave a clear record.

[PAUSE]

[JAMIE]
What should a learner do if they get stuck?

[ALEX]
If you cannot find an issue, search the Issues list with filters like is:open or label:bug. If @mention does not seem to work, make sure the username is correct and the symbol comes right before it. If sub-issues are missing, the repository may not have that feature enabled.

[JAMIE]
And if nothing lines up?

[ALEX]
Ask a facilitator for a direct link or a quick check. The goal is not to guess. The goal is to keep moving with enough confirmation that you trust the result.

[PAUSE]

[ALEX]
The learning moment in this chapter is that issues are collaborative spaces, not just task trackers. A clear title helps someone find the work. A good body helps someone understand it. Labels, comments, reactions, and references make the thread useful to everyone else.

[JAMIE]
That is a better way to think about it than just “file a ticket.”

[ALEX]
Exactly. The learning pattern used here is consistent: try a small action, read the result, then build from there. Create one issue. Comment on one issue. If enabled, split one issue into a smaller one. Each step should leave a visible trail you can point to later.

[PAUSE]

[JAMIE]
What about the learning cards in this chapter?

The learning cards are there to give just-in-time guidance. Some explain navigation. Some explain writing. Some explain what evidence to submit. They are not all meant to be read at once; they show up when they are useful.

[JAMIE]
So they are support, not clutter.

[ALEX]
Right. They are there to keep the workflow teachable without forcing the learner to remember everything before they begin.

[PAUSE]

[JAMIE]
What is the local Git alternative?

[ALEX]
If you cloned the repository to your computer, you can still work with issues from the terminal. Check your branch, list your assigned issues, view an issue, and leave a comment with gh. The point is to keep the issue work tied to the repository even when you are not in the browser.

[ALEX]
That is also a good reminder that issues and code work often live side by side. The issue describes the need. The branch and pull request carry out the change.

[PAUSE]

[JAMIE]
Before we finish, what should someone remember about the Issues list page?

[ALEX]
Look for the title, author, labels, and status. Use filters when the list is noisy. Open the issue when you need the details. Search with qualifiers when the list is too broad. That flow will save a lot of time.

[JAMIE]
And the final takeaway?

[ALEX]
A good issue is clear, searchable, and actionable. A good comment adds context. A good reference connects the work. Once those pieces feel natural, issue management stops being a chore and starts feeling like collaboration.
