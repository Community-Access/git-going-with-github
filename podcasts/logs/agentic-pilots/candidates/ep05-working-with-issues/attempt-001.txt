[JAMIE]
Now walk us through the product itself. What is a GitHub issue in plain terms?

[ALEX]
An issue is a numbered discussion thread tied to a repository. It has anatomy: title, body written in Markdown, labels, assignees, milestone, state (open or closed), and a timeline of comments, events, and references.

[ALEX]
Navigating to the Issues List has two routes. From a repository page, open the Issues tab. Or use a direct URL ending in slash issues. Learning Cards for this section focus on finding the page quickly and confirming where you landed.

[JAMIE]
Once we land on the list page, what should we read first?

[ALEX]
The Issues List Page gives a list view with filters and search at the top. Page structure matters: each row announces issue number, title, labels, author, and update activity. You can scan fast, then open the one you need.

[JAMIE]
Let’s do filtering and searching.

[ALEX]
Use the search/filter bar with qualifiers like is:open label:bug, author:username, assignee:username, milestone:"Sprint 1", and is:closed when you need finished work. Useful filter queries save time, and the filter buttons for Open and Closed give quick state toggles.

[JAMIE]
So both typed queries and button filters are valid paths.

[ALEX]
Right. Reading an issue means more than the first paragraph. Start with the description, then review comments and activity in the timeline. Quick navigation helps: jump between headings, landmarks, and form fields. Learning Cards here emphasize finding the problem statement, current status, and next action.

[PAUSE]

[JAMIE]
Now comments. What counts as a strong issue comment?

[ALEX]
Leaving a Comment should add context, ask a precise question, confirm reproduction, or propose a next step. Keep it specific. Use Markdown formatting while typing: lists, links, task lists, and fenced code blocks for logs or commands.

[ALEX]
GitHub shortcuts help too. On the Issues list page, use shortcuts to move and open items faster. On an open issue, jump to comment fields and submit efficiently. Reactions are lightweight feedback; a quick emoji reaction can acknowledge without adding noise.

[JAMIE]
And referencing other work?

[ALEX]
Use #number to reference another issue or PR directly. Mentioning another issue in a comment creates traceable links. Cross-repo references work with owner slash repo hash number. Closing keywords in PR descriptions or comments, like Fixes #42, connect code changes to issue closure.

[JAMIE]
Great. Now file a new one from scratch.

[ALEX]
Filing a New Issue starts at New issue. Then fill out the form with a clear title and descriptive body. A useful structure is: What happened, What I expected, How to reproduce, Environment, Additional context.

[ALEX]
In the body, Markdown is your friend: code blocks for exact output, numbered steps for reproduction, task lists for follow-up items, and links to related evidence. Then assign labels from the sidebar, add assignees, choose a milestone, and submit.

[JAMIE]
After submission, what management actions matter most?

[ALEX]
Assign the issue to yourself or a teammate. Apply or remove labels as understanding improves. Close the issue when the work is done or no longer needed. Closed means resolved or intentionally ended, not deleted. Reopen if new evidence shows it is still valid.

[PAUSE]

[JAMIE]
Give the terminal path too, since some learners prefer local workflows.

[ALEX]
Local Git Alternative: Working from Your Clone uses GitHub CLI. You can list issues, inspect one, comment, and create from terminal as an alternative to the web UI.

[ALEX]
Examples: gh issue list with filters, gh issue view 42, gh issue comment 42 --body "context", and gh issue create for guided filing. Same concepts, different interface.

[JAMIE]
That ties into the bigger picture: issues and pull requests are linked, not separate worlds.

[ALEX]
Exactly. Issues describe work and discussion; pull requests implement changes. Cross-references, timeline events, and closing keywords keep the chain of evidence intact from report to fix.

[JAMIE]
Before we close, what should learners keep in working memory?

[ALEX]
Know what an issue is, scan the list with filters, read timelines carefully, file with clarity, comment with purpose, and manage state deliberately. If something is closed too soon, reopen it and continue the thread with new context.
