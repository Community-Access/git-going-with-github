[JAMIE]
Set the stage. What are we working with?

[ALEX]
GitHub Projects is GitHub's built-in planning system. It links issues and pull requests into one shared workspace that teams can filter, group, and update together.

[ALEX]
One helpful habit is to confirm where you are before you interact with anything. Headings, tabs, and landmarks are not decoration; they are your navigation tools.

[ALEX]
There are two generations to know about: Classic Project Boards, and Projects v2. The current experience is Projects v2, and it is the one you will see on repos and organizations today.

[JAMIE]
What is the first big idea to hold onto?

[ALEX]
Projects can live at the organization level or the repository level. That one distinction shapes who can see the project and which work it can collect.

[JAMIE]
That already sounds less mysterious.

[ALEX]
Good. The point is not speed. The point is knowing what you are creating and why.

[PAUSE]

[JAMIE]
Walk me through creating one.

[ALEX]
Creating a Project starts with choosing the scope and then naming the workspace.

[ALEX]
From an organization, go to the org page, open the Projects tab, choose New project, and pick a template or start blank. Then give it a name and create it.

[JAMIE]
And from a repository?

[ALEX]
Go to the repository, open Projects, choose Link a project or New project, and follow the same naming and template flow.

[ALEX]
For screen reader users, the key is simple: the New project button is on the Projects tab, template cards are reachable in the creation dialog, and after creation you land in an empty project with an Add item control ready to use.

[PAUSE]

[JAMIE]
Now move into the layouts.

[ALEX]
Projects has three core views: Table, Board, and Roadmap.

[ALEX]
Table view is the spreadsheet-style layout. Each row is an item, and each column is a field like Title, Status, Assignee, Labels, or something custom you add. It is the best place for structured editing and for keyboard users.

[JAMIE]
What does keyboard navigation look like there?

[ALEX]
Use arrow keys to move through rows and columns. Press Enter to open an item and see its detail panel. For screen readers, each row should announce the item name followed by its key fields.

[ALEX]
Board view is the Kanban-style layout. Columns represent status buckets, and cards move between them as work changes.

[JAMIE]
Can someone change a card without dragging it?

[ALEX]
Yes. Open the card, focus the Status field in the detail panel, and select a new column value from the dropdown. That gives keyboard users the same outcome without drag-and-drop.

[ALEX]
Roadmap view is timeline-based. It shows items as bars across dates, which makes it useful for planning and visibility across time.

[JAMIE]
So dates matter there.

[ALEX]
They do. Set start and due dates, or use a milestone, and the item appears on the timeline. Without dates, it will not plot the same way.

[PAUSE]

[JAMIE]
How should someone think about these three views together?

[ALEX]
Table is for precision, Board is for flow, Roadmap is for time. If you need reliable reading or editing, Table is usually the safest starting point.

[ALEX]
Board cards can be compact, and Roadmap bars can be visually dense, so zoom and layout matter. Table is the most straightforward layout for screen readers and keyboard work.

[PAUSE]

[JAMIE]
Move into custom fields.

[ALEX]
Custom fields are one of the most useful parts of Projects v2. They let you add project-specific structure beyond the default GitHub fields.

[ALEX]
Field types include text, number, date, single select, and iteration. Text works for notes, number for estimates or points, date for scheduling, single select for fixed options, and iteration for sprint-style planning.

[JAMIE]
How do you create one?

[ALEX]
In Table view, scroll to the end of the field headers, activate the plus button, choose a field type, name it, and configure the options if needed. Once created, it becomes a new column.

[JAMIE]
And editing a value?

[ALEX]
Find the cell where the field and item intersect, press Enter or Space to edit, type the value or choose from the dropdown, then confirm with Enter or Tab.

[PAUSE]

[JAMIE]
Now add items.

[ALEX]
Projects can include existing issues, pull requests, and draft issues.

[ALEX]
To add an existing issue or PR, use Add item, search for the item, and select it. The item stays in its repository, but now it also appears in the project.

[JAMIE]
What about drafts?

[ALEX]
Draft issues live only inside the project until you promote them. They are great for early planning when you want to capture an idea before it belongs in a repo.

[ALEX]
To promote one, open the draft and convert it to an issue, then choose the repository it should belong to.

[JAMIE]
Can you bulk edit too?

[ALEX]
Yes. In Table view, select multiple items and update shared fields together. That is useful for quick status changes, assignments, or field cleanup.

[PAUSE]

[JAMIE]
Tell me about automations.

[ALEX]
Built-in automations are where Projects starts to save real time. You can access workflows from the project settings and use them to automate common status changes.

[ALEX]
Typical workflows include auto-add, auto-archive, and status updates when issues are closed or reopened. You can also connect project events with GitHub Actions for more advanced workflow logic.

[JAMIE]
So the project can react on its own.

[ALEX]
Exactly. The workflow should move work forward when the signal is obvious.

[PAUSE]

[JAMIE]
Now iterations.

[ALEX]
Iterations are sprint-like time blocks. Create an iteration field, define the length, and then assign items to the current or future iteration.

[JAMIE]
And that helps with planning?

[ALEX]
Yes. Iterations make it easier to see what is in a sprint, what is slipping, and what is ready to start. Insights can then show how the iteration is progressing.

[PAUSE]

[JAMIE]
How do filters and views fit in?

[ALEX]
Views let you create different lenses on the same project. You can make a view, apply filters, group items, and sort them in whatever way is useful.

[ALEX]
The filter syntax is powerful enough to narrow by fields, status, labels, assignee, and more. Grouping is what turns a flat list into something easier to scan.

[JAMIE]
So one project can support multiple workflows.

[ALEX]
Exactly. One source of truth, many views.

[PAUSE]

[JAMIE]
What changes when projects span repositories?

[ALEX]
Cross-repository projects let you track work from several repos in one place. That is the big win for teams that split work across services, libraries, or product areas.

[ALEX]
You can add repositories to the project and use the Repository field to keep items organized. That gives you a clean way to see where work lives without losing the unified plan.

[PAUSE]

[JAMIE]
Give me the accessibility navigation reference in plain language.

[ALEX]
On the project home page, move through the list of projects and open the one you need. Inside a project, use headings, tabs, and the current view controls to orient yourself.

[ALEX]
In Table view, use the grid semantics and arrow-key movement. In Board view, focus on the column and card structure. In the right-side detail panel, review and edit fields. In the filter bar, build queries carefully and confirm the results before continuing.

[JAMIE]
What is the accessibility-agent shortcut?

[ALEX]
The `/project-status` command gives a quick snapshot of project state. It is useful when you want a fast summary of items, status, or workload without manually browsing every view.

[ALEX]
Use it when you need a quick check during standup, before filing duplicate work, or when you are catching up after time away.
