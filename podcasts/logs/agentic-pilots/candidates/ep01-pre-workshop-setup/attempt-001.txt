[JAMIE]
Step 1 is account creation. What should people do carefully there?

[ALEX]
Create your GitHub account, verify your email, and choose your username thoughtfully because it appears on issues, pull requests, and comments.

[ALEX]
Use a clear, professional username pattern you can keep long-term.

[ALEX]
During signup: enter email, create password, choose username, complete human verification, then confirm the code GitHub sends to email.

[ALEX]
After account creation, open the verification email link to fully activate the account.

[JAMIE]
Then comes two-factor authentication.

[ALEX]
Yes. 2FA means sign-in requires two checks: your password plus a second factor. It protects your account if your password is exposed, and GitHub requires 2FA for active accounts in this workshop context.

[ALEX]
Quick setup path: Settings, Password and authentication, enable 2FA, then select method.

[ALEX]
Recommended order: GitHub Mobile push approval, then authenticator app, then security key or passkey, with SMS only as fallback.

[ALEX]
Detailed note for screen reader users: if QR scanning is awkward, use the text key option and enter it manually in your authenticator app.

[ALEX]
Recovery and backup are mandatory habits: save recovery codes in a secure place and register more than one second factor to avoid lockout.

[JAMIE]
And Git authentication later is browser-based OAuth in most beginner workflows, right?

[ALEX]
Correct. In VS Code, when you first push or pull, browser sign-in handles auth and stores credentials through your OS keychain flow.

[ALEX]
Workshop policy is straightforward: have a working GitHub account with 2FA enabled before Day 1.

[ALEX]
Learning card summary: tab through fields, listen for inline validation, complete verification, enable 2FA, store recovery codes safely.

[PAUSE]

[JAMIE]
Step 2 is GitHub accessibility settings. Which ones matter most?

[ALEX]
Start at Accessibility settings and apply these in order.

[ALEX]
1. Disable Hovercards first. They often create noisy, unexpected announcements for screen readers.

[ALEX]
2. Enable link underlines to improve link recognition at a glance.

[ALEX]
3. Character key shortcuts: keep them off unless you intentionally want single-key navigation behavior.

[ALEX]
4. Set your theme in Appearance to maximize contrast and reduce fatigue.

[ALEX]
Learning card: tune the interface so focus, links, and navigation stay predictable.

[JAMIE]
Step 5 is screen reader and browser setup. Give platform-specific guidance.

[ALEX]
For NVDA on Windows: use browse mode confidently, keep quick navigation keys handy, and choose a speech rate and punctuation level you can sustain during long sessions.

[ALEX]
For JAWS on Windows: confirm web verbosity, heading navigation, and forms mode behavior align with GitHub pages.

[ALEX]
For VoiceOver on macOS: verify web rotor usage, enable Quick Nav for faster movement, and remember Mac keyboard shortcut differences from Windows instructions.

[ALEX]
Browser summary: Chrome or Firefox are strong cross-platform choices, Edge is fine on Windows, and Safari pairs best with VoiceOver on macOS.

[ALEX]
Learning card: adjust speech, navigation mode, and browser pairing before workshop day, not during exercises.

[JAMIE]
Step 6 is tool installation: Git first, then VS Code.

[ALEX]
Exactly. Install Git before anything else.

[ALEX]
Windows: install Git for Windows, then verify in terminal with git --version.

[ALEX]
macOS: install Xcode Command Line Tools or Git package, then verify the same way.

[ALEX]
Linux: install Git from your distro package manager, then run git --version.

[ALEX]
Then configure identity:
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

[ALEX]
That identity is attached to your commits, so set it intentionally.

[ALEX]
Now install Visual Studio Code. It is recommended because workshop materials, extensions, Git integration, and accessibility support are consistent there.

[ALEX]
Enable VS Code screen reader mode either by keyboard shortcut or through Command Palette with "Toggle Screen Reader Accessibility Mode."

[ALEX]
If local install is blocked, github.dev is the browser-based editing alternative for many exercises.

[JAMIE]
Before we close, can we clarify Git versus GitHub in plain language?

[ALEX]
Git is the local version control system on your computer. GitHub is the online platform that hosts repositories, collaboration, issues, and pull requests built around Git workflows.

[ALEX]
You use Git to track and create history; you use GitHub to share, review, and collaborate on that history.

[JAMIE]
That distinction removes a lot of beginner confusion.

[ALEX]
Good. If your setup checks pass, you are ready for Day 1 with fewer surprises and more focus on learning.
