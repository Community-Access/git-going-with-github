What does someone need before Day 1 begins?

[ALEX]
First, the basics: a computer, a stable internet connection, and headphones if the room is busy or you want cleaner screen reader audio. On the software side, you need a GitHub account, a supported browser, a screen reader, Git, and Visual Studio Code.

[JAMIE]
So the big idea is that there is a hardware layer, a browser layer, and a developer tools layer.

[ALEX]
Yes. And if you are using agents or advanced accessibility features later, you also want current versions of your tools. But for this episode, the important thing is simple: get the core setup done before the workshop begins.

[ALEX]
Let’s start with the account. Create your GitHub account first if you do not already have one.

[JAMIE]
That means choosing a username too, right?

[ALEX]
Right. And that username matters. It shows up in issues, pull requests, comments, and anywhere else you contribute. Pick something you can live with in public, because it becomes part of your GitHub identity.

[JAMIE]
What else happens during signup?

[ALEX]
You verify your email address, and you complete the human verification step GitHub uses during account creation. Then, after the account is made, you check your inbox for the verification email and confirm that address as well.

[JAMIE]
And 2FA is not optional.

[ALEX]
Correct. Two-factor authentication is required. It means signing in needs a second proof beyond your password, like a push approval, an authenticator code, a security key, or a passkey. The reason is straightforward: if someone gets your password, 2FA still protects the account.

[JAMIE]
What is the easiest way to think about it?

[ALEX]
A password is one lock. 2FA adds a second lock. That second lock is what makes the account fit for workshop use.

[PAUSE]

[JAMIE]
How should someone set up 2FA without getting lost?

[ALEX]
Go to GitHub settings, open the security section, and start two-factor authentication. GitHub will walk you through the options. For most people, the easiest path is the GitHub Mobile app or an authenticator app. If you already use a security key or passkey, that is even stronger.

[JAMIE]
What should they keep in mind during setup?

[ALEX]
Recovery codes. Save them somewhere safe right away. If you ever lose your phone or key, those codes may be the only way back in. Also, it is smart to register more than one second factor so you do not end up locked out.

[JAMIE]
So the workflow is not just “turn it on.” It is “turn it on, save recovery, add backup.”

[ALEX]
Exactly.

[PAUSE]

[JAMIE]
What should they do about GitHub accessibility settings?

[ALEX]
Once signed in, adjust the settings that make GitHub easier to use with a screen reader and keyboard. The highest priority is disabling hovercards, because they can get in the way. Then enable link underlines, which makes links easier to identify. If you like keyboard shortcuts, check the character key shortcut setting too. And choose a theme that gives you comfortable contrast.

[JAMIE]
That sounds small, but it changes the feel of the site a lot.

[ALEX]
It does. The best accessibility settings are the ones that reduce friction before it starts.

[PAUSE]

[ALEX]
Next, update your profile. Add a profile picture if you can, choose a clear notification email, and make sure your account details are current.

[JAMIE]
Why does that matter in a workshop?

[ALEX]
Because maintainers and classmates need a reliable way to recognize you and reach you. A clean profile makes collaboration easier, especially when you start opening pull requests or commenting on shared work.

[PAUSE]

[JAMIE]
What about feature previews?

[ALEX]
Check GitHub feature preview settings too. Some features appear there before they become standard. You do not need every preview turned on, but it helps to know where that area lives in case a workshop step depends on it.

[JAMIE]
So it is a “know where to look” skill, not a “turn everything on” skill.

[ALEX]
Exactly.

[PAUSE]

[ALEX]
Now the screen reader and browser setup. If you are on Windows, NVDA or JAWS are both supported. If you are on macOS, VoiceOver is the default choice. The workshop is designed to work with all of them, so choose the one you already know best.

[JAMIE]
And the browser?

[ALEX]
Use a modern browser like Chrome, Firefox, Edge, or Safari on Mac with VoiceOver. The important part is consistency. Pick one browser, learn its navigation patterns, and keep it stable during the workshop.

[JAMIE]
What should be configured first?

[ALEX]
For NVDA, make sure web browsing features are on and that you are comfortable moving by headings, links, and form fields. For JAWS, confirm the same basic web navigation habits. For VoiceOver, turn on Quick Nav if that helps you move quickly through pages.

[JAMIE]
So the real goal is not a perfect setup screen. It is reliable navigation.

[ALEX]
That is the whole point.

[PAUSE]

[ALEX]
Now install Git. Git is the version control system itself. GitHub is the website and service built around it. They are related, but they are not the same thing.

[JAMIE]
That distinction matters, because people often use the names like they mean the same job.

[ALEX]
Exactly. Git lives on your machine and tracks changes to files. GitHub hosts repositories and collaboration tools online.

[JAMIE]
How do you install it?

[ALEX]
On Windows, download and install Git from the official Git site. On macOS, install Git through the Xcode Command Line Tools or the Git installer. On Linux, use your package manager. After that, open a terminal and verify it with `git --version`.

[JAMIE]
And that verification is the proof that the install actually landed.

[ALEX]
Yes. Do not assume. Check.

[PAUSE]

[JAMIE]
What comes next after Git is installed?

[ALEX]
Configure your Git identity. Set `user.name` and `user.email` so your commits are labeled correctly.

[JAMIE]
Why does that matter?

[ALEX]
Because Git uses that identity on your work. It helps your commits show up under the right name and email, and it keeps collaboration clean.

[JAMIE]
So this is not cosmetic. It is part of how your work is recorded.

[ALEX]
Right.

[PAUSE]

[ALEX]
Now install Visual Studio Code, or VS Code. That is the recommended editor for the workshop.

[JAMIE]
What makes it the recommendation?

[ALEX]
It is widely used, it works well with GitHub workflows, and it has strong keyboard support. It also has a screen reader mode, which is why it fits this workshop so well.

[JAMIE]
How should someone enable that mode?

[ALEX]
Install VS Code, open it, and turn on screen reader support. You can do that with the keyboard shortcut or from the Command Palette. Once it is on, VS Code speaks and behaves more predictably with assistive tech.

[JAMIE]
That is the part that makes the editor feel like a tool instead of an obstacle.

[ALEX]
Exactly.

[PAUSE]

[JAMIE]
What if someone wants to work in the browser instead?

Use github.dev. It is the browser-based editor alternative. You can open it from a repository and edit directly in the browser without installing a desktop editor.

[JAMIE]
So it is a backup path, not the main recommendation.

[ALEX]
Right. It is useful when you want a lightweight option or when a desktop setup is not available.
