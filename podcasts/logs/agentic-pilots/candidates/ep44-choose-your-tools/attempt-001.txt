Section 1, why this matters: there is no single right way to use GitHub. Strong contributors switch tools based on task, comfort, and access needs.

[JAMIE]
So multiple paths are a feature, not confusion.

[ALEX]
Right. Section 2, the five paths gives you options without forcing one identity.

[ALEX]
Section 3, Path 1: GitHub.com in the browser. This is the Day 1 foundation because everything lives here: repos, issues, pull requests, settings, and permissions.

[JAMIE]
What can you do here?

[ALEX]
Browse files, open and review pull requests, create and manage issues, edit single files with the pencil action, and handle repository settings.

[JAMIE]
And what can’t you do here?

[ALEX]
You cannot run local builds, use a full local extension stack, or work offline the same way as desktop tools.

[JAMIE]
Screen reader experience?

[ALEX]
Strong landmarks, reliable headings, keyboard-first navigation, and consistent page structure make it practical and learnable.

[JAMIE]
Low vision experience?

[ALEX]
Theme controls, high-contrast options, link-underlining options, and zoom behavior that stays usable at high magnification on most pages.

[JAMIE]
Learning cards for GitHub.com?

[ALEX]
Think in checkpoints: jump to search, move by landmarks, switch tabs with shortcuts, and confirm where you are before activating controls.

[PAUSE]

[ALEX]
Section 4, Path 2: github.dev, the browser-based editor. This is the bridge from browser workflow to editor workflow.

[JAMIE]
What can you do there?

[ALEX]
Edit across multiple files, view diffs, stage and commit changes, and use many web-compatible VS Code extensions.

[JAMIE]
What can’t you do there?

[ALEX]
No full local runtime: limited execution, no full offline workflow, and some extensions requiring local binaries will not work.

[JAMIE]
How do you open it?

[ALEX]
From a repo, press period, or change the URL to github.dev.

[JAMIE]
Screen reader experience?

[ALEX]
It inherits the VS Code interaction model: command palette, predictable keybindings, and structured panels.

[JAMIE]
When should someone pick github.dev over GitHub.com?

[ALEX]
When work spans multiple files in one change, and you want editor power without local setup.

[PAUSE]

[ALEX]
Section 5, Path 3: VS Code desktop, your full Day 2 workspace.

[JAMIE]
What can you do here?

[ALEX]
Local editing with IntelliSense, terminal workflows, Git operations, debugging, extensions, and offline-first development.

[JAMIE]
What can’t you do here without extensions?

[ALEX]
Native issue and pull request management is limited unless you add GitHub-focused extensions, and repository insights/settings still belong on GitHub.com.

[JAMIE]
Screen reader experience?

[ALEX]
Dedicated accessibility behavior, spoken editor state, and panel-level shortcut help.

[JAMIE]
Low vision experience?

[ALEX]
High-contrast themes, adjustable zoom and fonts, and layout controls like disabling minimap to reduce clutter.

[JAMIE]
Learning cards for VS Code?

[ALEX]
Focus Explorer, Source Control, Command Palette, theme picker, and zoom controls; each one gives you a stable place to recover when you lose context.

[PAUSE]

[ALEX]
Section 6, Path 4: GitHub Desktop.

[JAMIE]
What can you do here?

[ALEX]
Clone repos, switch branches, inspect diffs, stage changes, commit, and push with a visual Git client.

[JAMIE]
What can’t you do here?

[ALEX]
It is not a full editor and not a full issue/PR review surface with inline discussion depth.

[JAMIE]
Screen reader experience?

[ALEX]
Basic coverage is usable for key Git tasks, but depth and speed can vary by workflow.

[JAMIE]
When should someone choose GitHub Desktop?

[ALEX]
When they want Git operations in a visual interface and prefer minimal terminal use.

[PAUSE]

[ALEX]
Section 7, Path 5: GitHub CLI.

[JAMIE]
What can you do here?

[ALEX]
Clone, branch, commit, sync, inspect PRs and issues, and script repeatable workflows.

[JAMIE]
What can’t you do here?

[ALEX]
It does not replace a rich visual code editor, and discoverability can be harder for brand-new users.

[JAMIE]
Screen reader experience?

[ALEX]
Many users like terminal predictability and linear output, but command density can raise the learning curve.

[JAMIE]
When should someone choose GitHub CLI?

[ALEX]
When speed, automation, or keyboard-only control is the priority.

[JAMIE]
Learning cards for CLI?

[ALEX]
Memorize a small command set first, read output carefully, and confirm repo, branch, and remote before running high-impact commands.

[PAUSE]

[ALEX]
Section 8, which path should I start with.
Day 1 recommendation: begin on GitHub.com so core objects and workflow are visible.
Day 2 recommendation: move into VS Code for full local practice.
And switching paths is normal, not failure.

[JAMIE]
That matters for accessibility too.

[ALEX]
Exactly. Screen reader users and low vision users often choose tools per task: browser for structure, editor for depth, desktop client for visual Git, CLI for predictable command flow.

[JAMIE]
Learning cards for choosing a path?

[ALEX]
Pick by task, comfort, and access need; if friction spikes, switch tools without guilt.

[PAUSE]

Section 9, your first confidence exercise.
The task: open this repository and read README.md through your chosen path.

[JAMIE]
Walk the five routes.

[ALEX]
Path 1, GitHub.com: open repo page, select README.md, confirm the file content is visible.
Path 2, github.dev: open editor-in-browser, focus explorer, open README.md, confirm content panel.
Path 3, VS Code if set up: clone repo, open folder, open README.md, confirm editor tab content.
Path 4, GitHub Desktop: clone in Desktop, open in your editor, open README.md, confirm text appears.
Path 5, GitHub CLI: clone from terminal, enter repo, open README.md in terminal or editor, confirm first paragraph is readable.

[JAMIE]
What does success look like?

[ALEX]
You can name the tool you used, name the file you opened, and show the visible result.
