[ALEX]
Episode 24 is about a skill most contributors need early: using GitHub Discussions for community conversation without mixing it up with issue tracking.

[JAMIE]
Good, because people see another tab and wonder, "Is this where I ask, report, or build?"

[PAUSE]

[ALEX]
Big picture first: Discussions are threaded conversations on a repository or organization. They are for questions, ideas, announcements, and shared learning.

[JAMIE]
So not every problem starts as an issue.

[ALEX]
Exactly. Think of this as forum-style collaboration beyond Issues and Pull Requests.

[ALEX]
For workshop alumni, the support hub pattern still works: read pinned onboarding posts, search before posting, use Discussions for Q&A, and use Issues when something needs tracked action.

[JAMIE]
And the learning cards frame stays the same: name the concept, do the move, check the evidence.

[PAUSE]

[ALEX]
Table of contents in plain language: when to use Discussions vs Issues, how to navigate there, how categories work, how to create and join threads, how answers and polls work, how screen reader navigation works, and when to convert a discussion into an issue.

[JAMIE]
Let's start with the judgment call.

[ALEX]
Use Discussions for exploration and shared understanding. Use Issues for discrete work items. Use Pull Requests for proposed code changes.

[ALEX]
If someone asks "How should this behave?", that is usually a discussion. If the team decides "Implement this fix," convert or open an issue. If code is ready, move to a PR.

[JAMIE]
That one distinction removes a lot of noise.

[PAUSE]

[ALEX]
Common categories you will see: General, Q&A, Ideas, Show and Tell, and Announcements.

[JAMIE]
And each one signals intent before I read the full thread.

[ALEX]
Right. Q&A supports accepted answers, Ideas supports early brainstorming, Announcements are maintainer broadcasts, Show and Tell highlights community work, and General catches the rest.

[PAUSE]

[ALEX]
Navigating to Discussions has two entry points. From a repository, open the Discussions tab in the main navigation.

[ALEX]
From an organization, open organization-level Discussions for cross-repo community topics.

[JAMIE]
If the repo tab is missing, that usually means the feature is not enabled.

[ALEX]
Correct. Then you either use organization discussions or ask maintainers to enable repo discussions.

[PAUSE]

[ALEX]
Inside Discussions, categories organize the list. Navigating categories is easier if you use headings and landmarks.

[ALEX]
The side panel, left or right depending on width, usually shows category links with counts, pinned or announcement content, and sometimes active threads or tags.

[JAMIE]
So the panel is not decoration; it is orientation.

[PAUSE]

[ALEX]
Creating a discussion is a short path: activate New discussion, choose a category, add a clear title and body, then start discussion.

[ALEX]
Screen reader path: verify page heading, move by landmark to main content, find New discussion button, then work through category, title, and editor fields.

[JAMIE]
And search first, especially in Q&A.

[ALEX]
Yes. Search discussions before posting. It avoids duplicates and surfaces accepted answers quickly.

[ALEX]
Learning card version: clear title, scoped question, reproducible context, then submit.

[PAUSE]

[JAMIE]
What about participating once a thread exists?

[ALEX]
Read top post first, then replies in order. In Q&A, check whether an answer is already marked.

[ALEX]
Navigation pattern: headings for structure, article regions for replies, forms for reply inputs.

[ALEX]
Replying to a discussion uses the same editor behavior as issue comments. Replying to a specific comment uses nested reply under that comment.

[JAMIE]
And upvoting?

[ALEX]
Use upvotes on useful discussions and comments instead of "+1" replies. It helps maintainers prioritize signal.

[PAUSE]

[ALEX]
Marking an answer matters in Q&A. The author can mark one reply as accepted.

[ALEX]
Steps: find the correct reply, activate Mark as answer, confirm the Answered state and pinned accepted response.

[JAMIE]
That turns one thread into reusable documentation.

[ALEX]
Exactly.

[PAUSE]

[ALEX]
Polls are another discussion tool. In supported categories, create a poll by adding a question and options when drafting the thread.

[ALEX]
Voting is straightforward: choose an option and submit vote. After voting, you can review proportions and community direction.

[JAMIE]
Useful for quick preference checks before opening implementation issues.

[PAUSE]

[ALEX]
Screen reader navigation reference, fast version.

[ALEX]
Discussions list: use headings to move between sections, then links to open threads.

[ALEX]
Inside a discussion: move to main heading, scan original post, jump reply-by-reply, then locate reply form.

[ALEX]
NVDA note: heading and landmark navigation are the fastest orientation tools.

[ALEX]
JAWS note: region and heading shortcuts help track thread structure and reply controls.

[ALEX]
VoiceOver note: rotor by headings and landmarks keeps long threads manageable.

[PAUSE]

[ALEX]
Organization-level discussions are best for policies, shared announcements, and questions that span multiple repositories.

[JAMIE]
And accessibility agents?

[ALEX]
What is different here: they help with structure, summaries, and consistency, but humans still decide category, scope, and final action path.

[PAUSE]

[ALEX]
Now the companion topic: GitHub Gists.

[JAMIE]
Shareable snippets and notes, right?

[ALEX]
Exactly. A Gist is lightweight code or text sharing with version history.

[ALEX]
Use a Gist when you need to share a snippet or notes. Use a repository when you need project structure, collaboration workflows, and long-term ownership patterns.

[PAUSE]

[ALEX]
Creating a Gist via web: choose public or secret, add filename and content, then create.

[ALEX]
Screen reader navigation: verify heading, fill filename field, fill editor, then activate create action.

[ALEX]
You can add multiple files to one Gist when context needs more than one snippet.

[JAMIE]
And that maps to the same learning card style: name, move, evidence.

[PAUSE]

[ALEX]
Editing a Gist updates version history. Embedding a Gist lets you display it in web content. Cloning a Gist pulls it locally like a small repo. Forking creates your own copy to modify.

[ALEX]
Finding your gists: use profile Gists area. Discovering public gists: browse or search public listings.

[ALEX]
Gist comments work like lightweight discussion. To add a comment, open the Gist, move to comment form, enter text, submit.

[PAUSE]

[ALEX]
Security and privacy rules are simple.

[ALEX]
Public gists are visible and indexable.

[ALEX]
Secret gists are unlisted, not private; anyone with the URL can access them.

[ALEX]
Never place credentials, tokens, personal data, or proprietary material in a gist.

[JAMIE]
If something sensitive leaks, delete immediately and rotate credentials.

[ALEX]
Right, and assume copies may already exist.

[PAUSE]

[ALEX]
Example use case: sharing a screen reader configuration snippet so peers can compare settings quickly.

[ALEX]
Another use case: a quick markdown note you can link in a discussion.

[ALEX]
And for Q&A sites, a Gist can hold code with syntax highlighting and revision history while your answer links to it.

[JAMIE]
So the practical comparison is clear: Discussions for conversation, Issues for tracked work, PRs for code proposals, Gists for shareable snippets.

[ALEX]
That is the model to carry forward: pick the space that matches the outcome you need, then verify the interface confirms that choice.
