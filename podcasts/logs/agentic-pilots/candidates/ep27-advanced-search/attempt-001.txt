[JAMIE]
Set the stage. Where do we start?

[ALEX]
Start with **Finding Anything Across All of GitHub**. The search bar can run globally across GitHub, or inside a repository if you scope it with `repo:owner/name`.

[ALEX]
Also call out the **Table of Contents** framing: Search Interface, Scopes, Query Language, Issues and PRs, Code, Commits, Repositories, Users and Organizations, Practical Workshop Queries, and Saving Searches.

[ALEX]
For **1. The Search Interface**: press `/` to jump to search from almost anywhere, then type. That keyboard path is often faster than navigating filter menus.

[JAMIE]
What makes that teachable for beginners?

[ALEX]
Use a learning-card pattern: name the idea, give one move, show expected evidence. Move: press `/`, run a query, confirm results are grouped by type.

[ALEX]
And include both modes: global search and in-repository search. If you are inside a repo, qualifiers like `repo:community-access/accessibility-agents` keep results focused.

[JAMIE]
That is concrete.

[ALEX]
Right, and it reduces cognitive load.

[PAUSE]

[ALEX]
Next is **2. Search Scopes** and **3. The Core Query Language**. Scopes include repositories, code, issues, pull requests, users, and topics.

[JAMIE]
Where do qualifiers fit in?

[ALEX]
Qualifiers are key:value filters. Combine them with boolean logic to get precise results: `is:issue is:open label:accessibility org:community-access`.

[ALEX]
Cover common issue qualifiers: `is:open`, `is:closed`, `label:`, `author:`, `assignee:`, `milestone:`. For PRs: `is:pr`, `review:approved`, `draft:true`, `head:`, `base:`.

[ALEX]
Then teach date filters and sorting: `created:>2025-01-01`, `updated:<2026-01-01`, plus `sort:created-asc` or `sort:updated-desc`.

[PAUSE]

[JAMIE]
If someone only remembers one workflow for issues and PRs, what is it?

[ALEX]
Go straight to `github.com/issues` or `github.com/pulls`, then refine with qualifiers. That is **4. Searching Issues and Pull Requests** in action.

[ALEX]
Practical queries matter here:
`is:issue is:open no:assignee label:accessibility org:community-access`,
`is:issue is:open label:"good first issue"`,
`is:issue is:open label:"good first issue" language:python`,
`is:pr is:open review-requested:@me`,
`is:pr is:open mentions:@me`,
`is:issue is:open assignee:@me`,
`is:issue is:open updated:<2025-11-14`.

[JAMIE]
That sounds like a real daily checklist.

[ALEX]
It is, and it is reusable. The learning card here is: run the query, inspect the list, and decide the next action from evidence, not guesswork.

[ALEX]
Then transition to **5. Searching Code**: basic text search, function usage across a repo, and org-wide pattern search with qualifiers like `language:`, `path:`, `extension:`, `org:`, `repo:`.

[JAMIE]
Give one code example.

[ALEX]
`org:community-access language:typescript path:/src/ extension:ts "useKeyboardNavigation"` finds likely implementations across repos.

[ALEX]
Also include **6. Searching Commits**: keyword in commit message, specific author, date range, and commits touching a file using commit search qualifiers.

[PAUSE]

[ALEX]
After that, cover **7. Searching Repositories** and **8. Searching Users and Organizations**. Example repo query: `topic:accessibility language:typescript sort:stars-desc`.

[JAMIE]
And people search?

[ALEX]
Use user/org filters to find maintainers, contributors, or teams by name, org membership, and activity context.

[ALEX]
For **9. Practical Queries for This Workshop**, include: open contributions in `accessibility-agents`, duplicate-check an issue before filing, all accessibility issues in a project, your merged PRs, and recent discussions on a topic.

[PAUSE]

[JAMIE]

What is the final takeaway?

[ALEX]
