Now comparison time: **GitHub Flow vs Git Flow**.

[ALEX]
Under **What Git Flow Is**, it is a release-heavy branching model from an earlier era of scheduled shipping.

[ALEX]
In **How the Git Flow Cycle Works**, work lands in develop, then release branches, then main, with hotfix branches when needed.

[ALEX]
For **How GitHub Flow Differs**, it is simpler: short-lived branches off main and continuous integration through PRs.

[ALEX]
**When You Might See Git Flow**: enterprise release trains, mobile release gates, firmware, and legacy systems.

[ALEX]
**Why This Workshop Uses GitHub Flow**: it matches modern open source contribution on GitHub.

It happens **In writing**, so tone must be explicit because no vocal cues are present.

[ALEX]

[ALEX]

Now feedback mechanics: **The Anatomy of Helpful Feedback**.

[ALEX]
Step **1. Acknowledge what's working** so the author knows what to keep.

[ALEX]
Step **2. Identify the specific concern** with a concrete reference.

[ALEX]
Step **3. Explain why it matters** in terms of users, maintainability, correctness, or accessibility.

[ALEX]
Step **4. Suggest a path forward (when you can)** with an example or option.

[ALEX]
Step **5. Signal the weight of the concern**: blocker, strong suggestion, or minor nit.

[JAMIE]
That helps avoid vague or hostile review comments.

[ALEX]
Yes. Give code review feedback by being specific, kind, and code-focused.

[ALEX]
Receive code review feedback without making it personal; the goal is improving the change, not judging the person.

[PAUSE]

[ALEX]
Tone guidance sits under **Language and Tone**.

[ALEX]
**Prefer "we" or describe the code, not the person**: “This function may fail on null input” is better than “You broke this.”

[ALEX]
**Use tentative language for uncertainty**: “I might be missing context, but…”

[ALEX]
**Acknowledge cultural and language diversity** by writing plainly and avoiding slang-heavy shorthand.

[ALEX]
**Avoid urgency markers unless genuinely urgent** so you do not create unnecessary pressure.

[JAMIE]
Can we add inclusive language examples directly?

[ALEX]
Yes. Prefer “allowlist/blocklist” over exclusionary legacy terms, “primary/secondary” over master/slave patterns, and “folks” or “everyone” over gendered group labels when appropriate.

[ALEX]
Inclusive language matters because wording shapes who feels welcome and who keeps contributing.

Before we close, a quick help strategy. Ask questions as soon as you are blocked beyond a reasonable attempt.

[ALEX]
Frame questions with: goal, what you tried, where it failed, exact error text, and what decision you need.

[ALEX]
Example: “I’m updating the docs link in setup-guide.md. I tried searching for the new path, but found two candidates. Which URL is canonical?”

[JAMIE]
And if nobody replies quickly?

[ALEX]
Be patient. Maintainers are often volunteers with limited time. A polite follow-up after a reasonable interval is fine.

[ALEX]
If you disagree, do it respectfully: cite evidence, describe tradeoffs, and stay focused on outcomes for users and project health.
