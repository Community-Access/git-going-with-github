[ALEX]
Episode 3 is about navigating repositories: how to get your bearings, find files, read history, and decide what to do next without guessing.

[JAMIE]
I like that framing. We are not memorizing a page; we are learning how a repository works so the steps make sense later.

[PAUSE]

[ALEX]
A repository is a project folder tracked by Git. On GitHub, that repository page is where you explore the code, issues, pull requests, actions, settings, and the rest of the project surface.

[JAMIE]
So the page is not just a file list. It is the project hub.

[ALEX]
Exactly. When you land on a new repo, start with the same orientation every time: identify the page, hear the repository name, find the main landmarks, and confirm where the Code tab and file tree live.

[PAUSE]

[JAMIE]
What should a learner expect the first time they open a repository?

[ALEX]
The repository page usually opens on the Code tab. That is where the file tree is, where the README renders, and where you choose a branch. A good first pass is: identify the repo, read the description, scan the tabs, then move into the files.

[JAMIE]
And that gives them a repeatable map instead of a wall of controls.

[ALEX]
Right. The tabs matter because they separate the major jobs of the project. Code for files, Issues for work, Pull Requests for proposed changes, Actions for automation, and Settings for maintainers.

[PAUSE]

[JAMIE]
How do we teach the tab bar without making it feel abstract?

[ALEX]
Say it plainly: the tab bar is the project’s control center. Not every tab appears on every repository, but the common ones are Code, Issues, Pull Requests, Actions, and sometimes Settings. The point is to know what kind of activity lives behind each label.

[JAMIE]
And the labels themselves are useful evidence.

[ALEX]
Yes. The counts, selection state, and position all tell you where you are. If the Code tab is active, you are in the repository’s main browsing area. If another tab is active, you have moved into a different workflow.

[PAUSE]

[ALEX]
Now for the file table. On the Code tab, the file list shows folders and files, along with recent commit messages and how long ago each item changed.

[JAMIE]
That is the part learners use most often.

[ALEX]
It is. A folder is not the same as a file, and the difference matters. Folders contain other items and usually open another view of the repository. Files open a single file page. In the table, the name tells you what it is, the message tells you what changed, and the date tells you when.

[JAMIE]
So the row is already a summary of the project’s recent work.

[ALEX]
Exactly. If a row says the file changed recently, that is a clue. If the commit message mentions documentation, tests, or a bug fix, that gives you context before you open anything.

[PAUSE]

[JAMIE]
What do we tell people about the branch selector?

[ALEX]
The branch selector sits above the file list and shows which branch you are viewing. A branch is a line of work inside the repository. Repositories have branches so people can work on features, fixes, or experiments without changing the default line of work immediately.

[JAMIE]
And the default branch is usually main.

[ALEX]
Usually, yes. The default branch is the branch GitHub shows first unless the repository owner has chosen another one. It is often the stable, primary version of the project.

[JAMIE]
What happens inside the selector?

[ALEX]
You open it, see the list of branches and sometimes tags, and choose the one you need. Switching branches changes the files, history, and README content you are viewing. If you switch to a tag, you are viewing a named snapshot, often tied to a release.

[PAUSE]

[ALEX]
Cloning is the next big idea. Cloning means copying a remote repository to your computer so you can work with it locally.

[JAMIE]
That is different from just viewing the files on GitHub.

[ALEX]
Yes. GitHub has a few ways to get the code, and they are not interchangeable. `gh repo clone` is a GitHub CLI way to clone with sensible defaults. `git clone` is the standard Git command. Downloading a ZIP gives you a snapshot of the files, but not the full Git history or normal Git workflow.

[JAMIE]
So ZIP is a shortcut for reading, not a full Git workflow.

[ALEX]
Right. And cloning is not the same as forking. A fork creates your own copy of someone else’s repository on GitHub. A clone puts the repository on your machine. A branch is a separate line of work inside a repository. Fork, clone, and branch solve different problems.

[PAUSE]

[JAMIE]
That distinction is worth slowing down for.

[ALEX]
It is. Watching, starring, and forking are also different. Watching subscribes you to notifications. Starring bookmarks the repository for yourself. Forking creates a copy you control, usually so you can make changes and propose them back later.

[JAMIE]
So watch is attention, star is memory, fork is ownership.

[ALEX]
That is a great shorthand.

[PAUSE]

[JAMIE]
What about reading a single file?

[ALEX]
A file page gives you the file content, the file’s metadata, and the action buttons. If it is a Markdown file like `README.md`, GitHub renders it into readable sections. If it is code, you get the source view.

[JAMIE]
And the README is often the fastest way to understand the project.

[ALEX]
Yes. The README usually tells you what the project does, how to install it, how to use it, and where to start contributing. The About section on the repository page adds another layer: description, topics, and license. Those are often the quickest clues about purpose and reuse.

[PAUSE]

[ALEX]
The file action buttons matter too. They let you copy, download, view raw content, and sometimes edit directly in the browser if you have permission.

[JAMIE]
So the page is not just for reading. It is also for acting.

[ALEX]
Exactly. And if you need another perspective on a file, the blame view shows who last changed each line. That helps answer, “Who touched this recently?” and “Where did this line come from?”

[PAUSE]

[JAMIE]
Commit history is the other half of that story.

[ALEX]
Right. The commits list shows what changed, who changed it, and when. A commit page gives you the details of that change, including the message and the files affected. Reading commit history is how you trace the project’s recent decisions.

[JAMIE]
That is useful when the file itself does not tell the whole story.

[ALEX]
Very useful. You can often tell whether a change was a bug fix, a refactor, a docs update, or a release from the commit message and the surrounding history.

[PAUSE]

[JAMIE]
What if someone is trying to find a file fast?

[ALEX]
Use Go to File. It is the quickest way to jump to a filename without scrolling through the tree. That skill becomes important in large repositories where the file table is long.

[JAMIE]
So the sequence is: know the repo, choose the tab, then search when the tree gets big.

[ALEX]
Exactly. GitHub shortcuts make that faster once you know them. You can move around the repository sidebar, jump to tabs, and reach the file finder without starting from the top every time.

[PAUSE]

[ALEX]
Now for the practical distinction people often miss: the repository’s About section, topics, and license are not decoration. They tell you what the project is about, how it is categorized, and what you are allowed to do with it.

[JAMIE]
That matters for contributors and for people just evaluating a project.

[ALEX]
It does. If the About section says the project is a library, a learning resource, or a demo, that changes how you read the README and where you look next.

[PAUSE]

[JAMIE]
Can we turn this into a few real scenarios?

[ALEX]
Yes. Scenario one: if you want to know what the project does, open the README and the About section first. Scenario two: if you want a good file to edit, use the file table and recent commit messages to find something active but understandable. Scenario three: if you want to know who has been working on a file, use blame and then inspect commit history.

[JAMIE]
And scenario four?

[ALEX]
If you want to understand what changed in the last release, go to the release notes or the commit history around the release tag. Scenario five: if you want to contribute, start with the README, look for `CONTRIBUTING.md`, and then check issues labeled for newcomers.

What do we say when someone gets stuck?

[ALEX]
Pause and re-orient. Check the page title, the active tab, the branch selector, and the file path. If the screen reader announcement does not match what you expect, stop and confirm before moving on.

[JAMIE]
That is a good habit for every repo, not just this chapter.

[ALEX]
Exactly. The point is not speed. The point is confidence backed by evidence.
