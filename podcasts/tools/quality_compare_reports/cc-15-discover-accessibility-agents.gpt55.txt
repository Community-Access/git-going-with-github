[JAMIE]
Can we give examples without implying those are the only right choices?

[ALEX]
Definitely. One example is accessibility-lead. Its purpose is to coordinate accessibility reviews across a team. It acts as an orchestrator, which means it routes a request to a more specialized agent instead of doing every check itself.

[JAMIE]
So if I ask a broad accessibility question, the lead agent might decide, “this belongs to the ARIA specialist,” or “this belongs to the keyboard specialist.”

[ALEX]
Exactly. Another example is aria-specialist. ARIA stands for Accessible Rich Internet Applications, and it’s a set of roles, states, and properties that help assistive technologies understand custom interface patterns. That agent reviews whether ARIA is being used correctly in HTML or web components.

[JAMIE]
And that’s a good place where manual knowledge matters, because ARIA can help, but bad ARIA can also make things worse.

[ALEX]
Yes. A third example is keyboard-navigator. It looks at whether interactive elements can be reached and operated by keyboard, including tab order, focus management, shortcuts, skip links, and focus traps.

[JAMIE]
But it can’t press the Tab key for me in the real interface.

[ALEX]
Right. Its instructions may let it review code and point out likely problems, but actual keyboard behavior still needs human testing. That’s a perfect example of why guardrails matter.

[PAUSE]

[JAMIE]
Let’s pause on that word: guardrails. What are we looking for inside an agent file?

[ALEX]
Most custom agent files use the .agent.md format. At the top, there is YAML frontmatter. YAML is a structured text format, and the frontmatter usually includes metadata such as the agent name, description, model preferences, and tools the agent can use.

[JAMIE]
Tools meaning things like reading files, editing files, running commands, or using GitHub information?

[ALEX]
Exactly. After the frontmatter, the body explains the agent’s behavior. In this challenge, you’re specifically looking for the purpose, the responsibilities, and the guardrails. Purpose tells you why the agent exists. Responsibilities tell you what it is designed to do. Guardrails tell you what it should avoid, what it cannot verify, or when it should ask for human confirmation.

[JAMIE]
That makes the agent feel less mysterious. It’s not just “AI magic.” It’s a markdown file with instructions and boundaries.

[ALEX]
That’s the right read. Agents are configurable tools. You can inspect them, question them, and improve them.

[PAUSE]

[JAMIE]
The challenge also asks learners to run one agent. What does “run” mean here?

[ALEX]
It depends on the agent. Some are invoked in Copilot Chat with an at-mention, some are surfaced through VS Code commands or an agents window, and some have README instructions in their folder. So first, choose an agent that interests you. Then read its README or usage notes before you try it.

[JAMIE]
So we don’t just type random commands and hope.

[ALEX]
Right. A safe first run is small and specific. For example, you might ask, “@accessibility-lead review the heading structure of this file.” In the reference solution, the lead agent delegates to a heading-focused specialist, which notices that a document jumps from an H2 heading to an H4 heading.

[JAMIE]
That’s useful, but I’d still open the file and check the heading sequence myself.

[ALEX]
Yes. The agent’s output is evidence to review, not a verdict to accept automatically. You compare it with your own understanding. If it found a heading skip, you verify the headings. If it suggests an ARIA change, you check whether the element actually needs ARIA.

[JAMIE]
And if the output seems wrong?

[ALEX]
Say so in your notes. A good evaluation can say, “The agent identified one issue correctly, but it missed another,” or “The recommendation needs manual testing.” Challenge 15 has no autograder for agent quality because human judgment is part of the work.

[JAMIE]
There are also slash commands and prompts in the reference material. How do those fit with agents?

[ALEX]
A slash command is a reusable prompt you can call by name, usually starting with a slash. A prompt file, often ending in .prompt.md, can define that reusable workflow. An agent file defines a persona and tools; a prompt file defines a repeatable task.

[JAMIE]
So an agent is more like, “who is helping me and what are they allowed to do,” while a prompt is, “what workflow am I asking for right now.”

[ALEX]
Nicely put. There are also instruction files, like .github slash copilot-instructions.md, that provide always-on project guidance. For example, a repository can tell Copilot about accessibility standards, documentation tone, or commit message style.

[JAMIE]
And AGENTS.md or CLAUDE.md may appear for other tools or compatibility.

[ALEX]
Yes. Appendix L is the deep reference for those file types. It explains user-level files, workspace-level files, and organization-level instructions. It also explains priority: when multiple instruction sources apply, the more specific or higher-priority source can win when there is a conflict.

[JAMIE]
That sounds like something I don’t need to master today, but I should know it exists.

[ALEX]
Exactly. For Challenge 15, your anchor is the .agent.md file: frontmatter, purpose, responsibilities, and guardrails.

[PAUSE]

[JAMIE]
What about agent skills? I saw references to SKILL.md files.

[ALEX]
A skill is reusable procedural knowledge. A SKILL.md file can describe when to use a skill, what steps to follow, and what output format to produce. Agents can draw on skills so the same process can be reused across different agents or contexts.

[JAMIE]
And hooks?

[ALEX]
Hooks are automation points that run around tool use or lifecycle events in some environments. They can enforce rules or require permission before a risky action. For a beginner, the main lesson is simple: if an agent has permission to edit files, run commands, or interact with GitHub, pay closer attention to the tool list and the guardrails.

[JAMIE]
Because a read-only helper and a file-editing helper carry different risk.

[ALEX]
Exactly. Some agents are informational, which means they mainly read and summarize. Others are task-oriented, which may edit files, run shell commands, or use APIs. Interactive wizard agents guide you through questions, like an issue template builder.

[JAMIE]
That distinction helps me decide how cautious to be.

[ALEX]
Yes. If an agent proposes a change, review the diff. If it runs a command, understand what the command does. If you don’t understand, ask it to explain before you allow the next step.

What if an agent isn’t found when I type its at-mention?
