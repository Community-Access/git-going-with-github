Challenge 2: File Your First Issue

Source template: challenge-02-first-issue.yml

Chapter: Ch05: Working with Issues

What you will do: Find a TODO comment in docs/welcome.md, then file an issue describing the problem with a clear title and description.

Instructions

  1. Open docs/welcome.md and look for a line that contains TODO -- this marks something that needs fixing.
  2. Go to the Issues tab and select New issue.
  3. Write a clear, descriptive title (not just "Fix TODO").
  4. In the description, explain:
    • What needs to change
    • Where the problem is (file name and what section)

What makes a good issue title?

Instead of this Write this
Fix TODO Fix missing workshop description in welcome.md
Bug welcome.md TODO placeholder needs real content
Update file Replace TODO in welcome.md intro section with actual welcome text

Instructions

  2. Find the branch dropdown (it shows "main" by default).
  3. Type learn/YOUR-USERNAME (replace YOUR-USERNAME with your actual GitHub username).

Challenge 6: Open Your First Pull Request

Source template: challenge-06-first-pr.yml

Chapter: Ch06: Working with Pull Requests

What you will do: Open a pull request from your learn/YOUR-USERNAME branch to main, connecting it to the issue you filed in Challenge 2.

Instructions

  1. Go to the Pull requests tab.
  2. Select New pull request.
  3. Set base to main and compare to learn/YOUR-USERNAME.
  4. Write a descriptive PR title.
  5. In the PR description, include Closes #XX (replace XX with your Challenge 2 issue number). This automatically links and closes the issue when the PR is merged.
  6. Submit the pull request.

PR description template

Use this structure for your PR description:

## What this PR does
[One sentence describing your change]

## Why
[One sentence explaining why this change is needed]

Closes #XX

The magic of Closes #XX

When you write Closes #12 in a PR description, GitHub automatically:

  • Links the PR to issue #12
  • Closes issue #12 when the PR is merged

This is one of GitHub's most powerful workflow features.

Challenge 7: Survive a Merge Conflict

Source template: challenge-07-merge-conflict.yml

Chapter: Ch07: Merge Conflicts

What you will do: Your facilitator will trigger a merge conflict in your PR. You will resolve it by editing the file, removing conflict markers, and keeping the right content.

What are conflict markers?

When Git cannot automatically merge changes, it inserts markers like this:

<<<<<<< HEAD
The version currently on the target branch
=======
Your version from your branch
>>>>>>> learn/your-username

Your job: decide what the final version should look like, then delete all three marker lines (<<<<<<<, =======, >>>>>>>).

Instructions

  1. Wait for your facilitator to trigger the conflict (they will tell you when).
  2. Open your PR -- you will see a message about conflicts.
  3. Select Resolve conflicts (or edit the file directly on your branch).
  4. Find the conflict markers in the file.
  5. Decide which content to keep (or combine both).
  6. Delete all conflict marker lines.
  7. Commit the resolution.

Autograded: The autograder will check that no conflict markers remain in your file and that the file has meaningful content.

Challenge 10: Go Local

Source template: challenge-10-go-local.yml

Chapters: Ch11: VS Code Interface | Ch13: How Git Works | Ch14: Git in Practice

What you will do: Clone the learning-room to your computer, create a feature branch, make an edit, commit locally, and push to GitHub.

The local workflow

This is the professional Git workflow you will use for the rest of your career:

  1. Clone the repository to your computer
  2. Branch -- create a new branch for your work
  3. Edit -- make your changes
  4. Commit -- save a snapshot locally
  5. Push -- send your branch to GitHub

Instructions (choose your tool)

VS Code (recommended for Day 2):

  1. Open VS Code. Open the Command Palette (Ctrl+Shift+P / Cmd+Shift+P).
  2. Type "Git: Clone" and paste the repository URL.
  3. After cloning, create a branch: open the Command Palette, type "Git: Create Branch", name it fix/YOUR-USERNAME.
  4. Edit any file in the docs/ folder (fix a typo, improve a sentence, add a comment).
  5. In the Source Control panel (Ctrl+Shift+G), stage your change, write a commit message, and commit.
  6. Push: open the Command Palette, type "Git: Push".

GitHub Desktop:

  1. File > Clone Repository. Paste the URL.
  2. Branch > New Branch. Name it fix/YOUR-USERNAME.
  3. Open the repo folder in your file manager, edit a file.
  4. In GitHub Desktop, write a commit message and commit.
  5. Select "Publish branch" to push.

CLI:

git clone <repo-url>
cd learning-room
git checkout -b fix/YOUR-USERNAME
# edit a file
git add .
git commit -m "fix: improve docs section"
git push -u origin fix/YOUR-USERNAME

Challenge 12: Review Like a Pro

Source template: challenge-12-review.yml

Chapter: Ch15: Code Review

What you will do: Give the peer-simulation PR a thorough code review with inline comments, a suggestion, and a verdict. If your facilitator gave you access to a real buddy's PR, you may review that PR instead.

Instructions

  1. Open the Peer Simulation: Improve contribution guidance PR. If you have real buddy access, you may open your buddy's Day 2 PR instead.
  2. Go to the Files changed tab.
  3. Review the changes and leave at least two inline comments:
    • One specific observation about something they did well
    • One constructive suggestion for improvement
  4. Use the Suggest changes feature for at least one of your comments (select the +/- icon in the comment toolbar to create a code suggestion block).
  5. Submit your review with a verdict: Approve, Request changes, or Comment.

Review checklist

When reviewing, consider:

  • Does the change do what the PR description says?
  • Is the commit message clear?
  • Are there any typos or formatting issues?
  • Would someone reading this file for the first time understand the changes?
  • Is the content accessible (clear language, proper Markdown formatting)?

The three verdicts

Verdict When to use it
Approve The changes are good and ready to merge
Request changes Something needs to be fixed before merging
Comment You have feedback but are not blocking the merge

Challenge 13: AI as Your Copilot

Source template: challenge-13-copilot.yml

Chapter: Ch16: GitHub Copilot

What you will do: Use GitHub Copilot to improve a documentation file, then critically evaluate whether the AI's suggestions are actually improvements.

Instructions

  1. Open the sample file: docs/samples/copilot-improvement-before.md (or any documentation file in the repo).
  2. Use GitHub Copilot (Chat or inline suggestions) to:
    • Improve the clarity of a paragraph
    • Fix any grammar or spelling issues
    • Suggest a better heading or structure
  3. Critically evaluate the AI's output before accepting it.

The trust-verify-reject framework

For every Copilot suggestion, ask yourself:

Question If yes If no
Is this factually accurate? Consider accepting Reject immediately
Is this clearer than the original? Consider accepting Keep the original
Does this match the tone of the document? Consider accepting Modify or reject
Does this introduce accessibility issues? Reject or fix Consider accepting
Did the AI add content I did not ask for? Review carefully Likely fine

What to watch for

AI can be confidently wrong. Watch for:

  • Hallucinated links -- URLs that look real but go nowhere
  • Over-complicated language -- simpler is usually better
  • Lost context -- the AI may not understand the workshop's audience
  • Accessibility regressions -- images without alt text, complex tables where lists work better

Challenge 14: Template Remix

Source template: challenge-14-template.yml

Chapter: Ch17: Issue Templates

What you will do: Create your own custom issue template by studying the existing registration template and remixing it for a new purpose.

Instructions

  1. Study the sample template at docs/samples/chapter-15-registration-remix-example.yml to understand the YAML format.
  2. Create a new file at .github/ISSUE_TEMPLATE/YOUR-USERNAME-template.yml on your branch.
  3. Your template must include:
    • A name field (required -- the autograder checks for this)
    • A description field
    • A title field with a prefix pattern
    • At least one textarea or input field in the body
  4. Choose your own topic. Ideas:
    • Accessibility feedback form
    • Workshop improvement suggestion
    • Bug report for a specific tool
    • Feature request with structured fields
  5. Commit and push your template.

Minimum YAML structure

name: "Your Template Name"
description: "One sentence describing when to use this template."
title: "[PREFIX] "
labels: ["your-label"]
body:
  - type: textarea
    id: details
    attributes:
      label: "Details"
      description: "Describe your request."
    validations:
      required: true

Challenge 15: Meet the Agents

Source template: challenge-15-agents.yml

Chapter: Ch19: Accessibility Agents

What you will do: Explore the accessibility-agents repository, discover what agents are available, run one agent, and read one agent's .agent.md file to understand how it works.

Instructions

  1. Discover -- Browse the accessibility-agents repository and find at least 3 different agents. Note their names and what they do.
  2. Run -- Choose one agent and try it out. This might mean:
    • Using a slash command in GitHub Copilot Chat
    • Invoking an agent through the VS Code command palette
    • Following the usage instructions in the agent's README
  3. Read -- Open one agent's .agent.md file. Identify:

What to look for in an .agent.md file

Every agent file follows a pattern:

  • YAML frontmatter at the top: metadata like name, description, tools
  • Responsibilities section: what the agent is designed to do
  • Guardrails section: boundaries that keep the agent safe and focused

Challenge 16: Build Your Agent (Capstone)

Source template: challenge-16-capstone.yml

Chapters: Ch18: Fork and Contribute | Ch20: Build Your Agent

What you will do: This is the capstone project. You will fork the accessibility-agents repository, write your own agent file, open a cross-fork pull request, and review a peer or facilitator-seeded agent.

Phase 1: Fork

  1. Go to the accessibility-agents repository.
  2. Select Fork to create your own copy.
  3. Clone your fork to your local machine.

Phase 2: Branch

  1. Create a branch named agent/YOUR-USERNAME for your work.

Phase 3: Write your agent

  1. Create a new file: agents/YOUR-AGENT-NAME.agent.md
  2. Your agent file must include:
    • Valid YAML frontmatter with name, description, and at least one tools entry
    • Responsibilities section -- 3-5 bullet points describing what your agent does
    • Guardrails section -- 2-3 bullet points describing what your agent should NOT do

Use this template to get started:

---
name: "Your Agent Name"
description: "One sentence describing what your agent does."
tools: ["codebase"]
---

# Your Agent Name

## Responsibilities

- Responsibility 1
- Responsibility 2
- Responsibility 3

## Guardrails

- Never do X
- Always verify Y before Z

Phase 4: Open a cross-fork PR

  1. Commit your agent file and push to your fork.
  2. Go to the original accessibility-agents repository.
  3. Open a pull request from your fork's branch to the original repo's main branch.
  4. Write a PR description that explains your agent's purpose.

Phase 5: Peer review

  1. Review a classmate's capstone PR if facilitator access is available. If not, review the peer-simulation PR and explain what you would look for in an agent PR.
  2. Check: Does their agent have responsibilities? Guardrails? Valid YAML?

Autograded: The autograder verifies that your agent file exists, has valid YAML frontmatter, and contains both responsibilities and guardrails sections.

Bonus A: Improve an Existing Agent

Source template: bonus-a-improve-agent.yml

For students who: Finish early and want to contribute more to the accessibility-agents ecosystem.

What you will do: Choose an existing agent in the accessibility-agents repository, identify something that could be better, and open a PR with your improvement.

Instructions

  1. Browse the agents in the accessibility-agents repository.
  2. Pick one that interests you and read its .agent.md file carefully.
  3. Identify an improvement. Ideas:
    • Add a missing guardrail
    • Clarify a responsibility that is vague
    • Fix a typo or improve the description
    • Add a new responsibility that fits the agent's purpose

Improvement criteria

Good improvements are:

  • Specific -- change one thing well, not many things vaguely
  • Justified -- explain WHY the change makes the agent better
  • Respectful -- the original author made choices for reasons. Improve, do not rewrite.
